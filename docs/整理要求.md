# 发票整理要求（规范 v1.1）

> **来源**：从参考案例 `<参考案例目录>` 反推出的整理方式，逐条固化成本文件。
> **性质**：这是验收标准。改动本文件 = 改动业务行为，属于 AGENTS.md 第 5 节的"未经明确要求不得做"。
>
> **v1.1（2026-10-06）**：新增**第二个来源**——微信入站目录。老板的长期指示是「以后的发票都丢给微信对话统一归档」。

## 0. 票据从哪里来（两个来源，合并成一次运行）

| | 来源一：邮箱 | 来源二：微信 |
|---|---|---|
| 取件位置 | QQ 邮箱 INBOX（IMAP 只读） | `<微信入站目录>\` |
| 窗口口径 | 邮件接收日 ∈ `[since, before)` | 文件名日期前缀（`YYYY-MM-DD_...`）∈ `[since, before)`；无前缀退回文件修改时间 |
| 收什么 | PDF 作发票载体；XML/OFD 作同伴；行程单另挂 | **只收 `.pdf`** |
| 不收什么 | —— | **图片不收**（聊天图太多，只进 `skipped` 留痕）；`.ofd`/`.xml` 不收（随机文件名无法按基名合并多格式） |
| 去重 | 按发票号码 | 先按 **md5** 去重（同一条消息可能落 .jpg + .png 两份），再并入全局按发票号码去重 |
| 非文档文件 | 不适用 | `.silk` 语音等**只记计数**，不逐条进跳过清单 |
| 上下文 | 有邮件正文 → 住宿票能认出城市/入住日期 | **无正文** → 住宿票认不出城市、行程谈不上闭环，按方案 A 进存疑 |

**合并优先级**：邮箱来源排在微信来源**前面**。同一张发票两边都来时，去重保留**先到的邮箱记录**——它带着邮件正文，上下文更全。

**节奏**：两个来源都在**每月 20 号那一趟**统一整理，不做实时监听。

**已定口径（2026-10-06 老板拍板）**：微信来源的差旅费票据若没有杭州往返凭证，**按方案 A 进存疑，不补上下文、不改规则、不计入总额**。

## 0.5 归档节奏、目录命名与排除（2026-10-06 定的口径）

### 目录命名：看"什么时候跑"

| 什么时候跑 | 目录名 | 为什么 |
|---|---|---|
| **月中**（运行日 < 20） | `{运行日}月度发票归集` | **不带总额** —— 这个月后面还会再进票，总额没定 |
| **每月执行日**（运行日 ≥ 20） | `{运行日}月度发票归集({计入总额})` | 总额已确定，写进名字 |

用 `--monthly` / `--mid-month` 可以强制指定；默认按运行日的日号自动判断。

### 执行日统一查重与合并

每月执行日那趟跑完之后，会自动**合并同一采集窗口的月中临时目录**（那是月中提前生成的）：

- 只有当月中目录里的**每一张发票都能在新目录里按发票号码找到**时才删除它；
- 少一张就**保留并报告**，绝不拿"反正差不多"去赌；
- 合并动作会写进运行日志。

查重本身靠**发票号码**：同一个月里无论收集多少次、发票从邮箱还是微信来，同一号码只计一次。

### 排除清单（作废 / 交由他人报销 / 月中已报销）

按**发票号码**把某些票从归档与统计里剔除。用途：

- 作废或开错的票；
- **已交由他人报销**、不由本工具重复计入的票；
- **月中已经报销过**的票，月末整理时不重复计入（用户会明确说明，台账要记准）。

管理方式：

```bash
python scripts/manage_exclusions.py list
python scripts/manage_exclusions.py add <发票号码> --reason "交由他人报销" --note "..."
python scripts/manage_exclusions.py remove <发票号码>
```

**硬规则**：

1. 每条排除**必须写原因**，会落进 `00_审计摘要.json -> skipped.excludedByNumber`（含金额、原因、备注、来源路径）；
2. **源文件一律不删** —— 排除只影响归档与统计，不影响 `assets/inbound/` 或 `assets/invoices/` 里的原件；
3. 排除按号码生效：同一号码若投递过多次，**全部**都会被排除，并各自留一条痕。

## 1. 一次运行产出什么

每次运行产出**一个自包含的运行目录**，命名：

```
{运行日 YYYYMMDD}月度发票归集({计入总额:.2f})
```

实例：`20261020月度发票归集(12849.96)`

目录内容（与参考案例同构）：

```
{运行目录}/
├── 00_审计摘要.json                    # 机器可读的统计口径与结果
├── 00_发票审计明细及汇总.xlsx           # 给人看的两张表
├── 00_汇总发票/
│   ├── 合并清单.json
│   └── {抬头}{用途}-{金额:.2f}元.pdf    # 每个分类一份，仅含计入总额的发票
├── 01_浙江大学明细/
│   ├── 01_差旅费/{行程文件夹}/...
│   ├── 02_招待费/...
│   └── 03_杭州市内打车票/...
├── 02_芯智辰光明细/                      # 同构
├── 99_存疑待人工审计/{存疑原因}/...
└── _原始数据/{序号}_*.xml                # 结构化原始数据备查
```

## 2. 分类规则（先抬头，再用途）

### 2.1 抬头（购买方）

按**发票购买方**判定，按以下顺序识别：

1. XML 的 `EInvoiceData/BuyerInformation/BuyerIdNum` 命中已知税号；
2. XML 的 `BuyerInformation/BuyerName` 命中已知名称；
3. PDF 全文命中已知抬头关键词；
4. 都不中 → `抬头待核`，进 `99_存疑待人工审计/未识别到指定抬头/`。

已知抬头（写在 `config.json -> classify.buyers`，顺序决定明细目录编号）：

| 抬头名 | 全称 | 统一社会信用代码 | 明细目录 |
|---|---|---|---|
| 浙江大学 | 浙江大学 | 12100000470095016Q | `01_浙江大学明细` |
| 芯智辰光 | 芯智辰光科技（杭州）有限公司 | 91330106MAKD4B5L0R | `02_芯智辰光明细` |

### 2.2 用途

| 用途 | 判定条件 | 明细目录 |
|---|---|---|
| 杭州市内打车票 | 票据类型=打车 **且** 行程单城市 = 杭州 | `03_杭州市内打车票` |
| 招待费 | 项目名称含 餐费/餐饮/糕点 | `02_招待费` |
| 差旅费 | 其余（打车、动车高铁、机票、住宿等） | `01_差旅费` |

**分类名 = 抬头 + 用途**，即 `浙江大学差旅费`、`芯智辰光招待费`、`浙江大学杭州市内打车票`。

### 2.3 票据类型

| 票据类型 | 判定 |
|---|---|
| 打车 | 有配对行程单，或项目名称含 客运服务 / 客运服务费 |
| 动车高铁 | 全文含 `铁路电子客票` 且不含退票字样 |
| 动车高铁退改签 | 全文含 `铁路电子客票` 且含 `退票` / `差额退票` |
| 机票 | 项目名称含 机票 / 代订机票 / 机票款 |
| 住宿 | 项目名称含 住宿 / 代订住宿 |
| 招待费 | 项目名称含 餐费/餐饮/糕点（票据类型与用途同名） |
| 其他 | 兜底 |

## 3. 命名规则（逐字符照抄参考案例）

### 3.1 发票 / 行程单

```
{序号:03d}_{日期}_{地点或路线}_{票据类型}_{金额:.2f}元_发票{发票号码后6位}_发票.pdf
{序号:03d}_{日期}_{地点或路线}_{票据类型}_{金额:.2f}元_发票{发票号码后6位}_行程单.pdf
```

- `{序号}`：该次运行内的全局流水号，从 001 起，**发票与它的行程单共用同一序号**。
- `{日期}`：优先用**行程/乘车日期**；无则用开票日期；再无法确定则写 `日期待核`。跨天写 `YYYY-MM-DD至YYYY-MM-DD`。
- `{地点或路线}`：行程单城市（`杭州`）、铁路站点对（`杭州西-上海南`）、航段（`杭州-北京`）；无法确定写 `地点待核` / `铁路地点待核` / `航程待核`。
- `{金额}`：**价税合计**（含税总额），保留 2 位小数。
- `{发票号码后6位}`：20 位发票号码取后 6 位；未识别到号码写 `未识别`。
- 文件名中不允许出现 `<>:"/\|?*`，空白折叠删除，长度上限 150。

### 3.2 行程文件夹（差旅费专用）

```
{NN}_{start}_至_{end}_{城市}差旅_{路线}
```

实例：`01_2025-09-06_至_2025-09-08_北京差旅_杭州-北京-杭州`

- 同日往返时 `{start}` 与 `{end}` 相同，仍写作 `A_至_A`。
- `{路线}` 能确认为杭州往返闭环时写 `杭州-{城市}-杭州`，否则省略。
- 无法归入任何行程的差旅费发票，直接放在 `01_差旅费/` 下并标存疑。

### 3.3 分类合并 PDF

```
{分类}-{金额:.2f}元.pdf
```

实例：`浙江大学差旅费-1234.56元.pdf`

- 只合并**计入总额**的发票，**不含行程单**（与参考案例口径一致）。
- 每张发票加一个书签：`{日期}_{金额:.2f}元_{原文件名}`。
- 页面数必须与源文件页数之和一致，否则整次运行失败。

## 4. 去重与配对

1. **去重主键 = 发票号码**（20 位）。同一号码只保留 1 条记录，金额只计一次。
2. 无号码时退化主键 = `(金额, 开票日期, 销售方名称)`。
3. 同一封邮件里同一张发票可能同时带 PDF/XML/OFD，**这些算一张发票**：按基名分组，XML 用于解析，PDF 用于归档，OFD 忽略。
4. 行程单与发票配对：同邮件内基名相同（去掉"发票/行程单"后缀后一致）**或**（父目录相同 且 金额差 ≤ 0.01）。一张行程单只能配一张发票。
5. 未配对上的行程单 → `99_存疑待人工审计/行程单未匹配发票/`，**不计入总额**。

## 5. 存疑（不进正常分类，全部进 `99_存疑待人工审计/{原因}/`）

| 存疑原因 | 触发条件 | 来源 |
|---|---|---|
| 未识别到指定抬头 | 抬头待核 | 参考案例原文 |
| 未能确认杭州出发并返回杭州的行程闭环 | 差旅费发票推导不出城市，无法归入任何行程 | 参考案例原文 |
| 杭州市外行程缺少杭州往返闭环凭证 | 能推导出城市，但该行程没有杭州↔该城市的交通凭证 | 参考案例原文 |
| 未匹配到发票的行程单 | 行程单无对应发票 | 参考案例原文 |
| 图片格式发票无法解析 | 附件为图片且无文本层 | 参考案例原文 |
| 重复发票不重复计入 | 发票号码（或退化主键）重复 | 参考案例原文 |
| 缺少PDF版发票文件 | 只有 XML/OFD，没有可归档可合并的 PDF | 本工具新增 |
| 打车发票未匹配行程单，城市待核 | 打车发票没有配对的行程单 | 本工具新增 |
| 无法解析发票内容 | 有 PDF 但两种提取器都读不出文本 | 本工具新增 |
| 行程单金额与发票金额不一致 | 两者金额差 > 0.01 | 本工具新增 |

**参考案例里有、本工具不再产生的两条**（自动化后不可达）：

- 「行程单城市为{城市}，与杭州室内分类不一致」——参考案例靠人工目录判断是否属于"杭州市内"，
  本工具改为**以行程单城市为准**：城市 = 杭州 → `杭州市内打车票`，否则 → `差旅费`，
  因此这条不自洽的情况从构造上就不可能出现。
- 「与4份单独发票重复，仅保留备查」——本工具按发票号码去重，重复项统一记为「重复发票不重复计入」。

**计入总额口径**：只有进入 `01_{抬头}明细` 或 `02_{抬头}明细` 的记录才计入；`99_存疑` 一律 `计入总额=否`。

**与参考案例的一处已知偏差**：参考案例把「芯智辰光住宿费」单独作为一个分类（1 张 146.00 元），
本工具把 住宿 统一归入 `差旅费`。理由：参考案例里"住宿"只在芯智辰光明细下单独成类，
在浙江大学明细下又并入了差旅费，属于人工归档的偶发不一致，不宜固化进自动化规则。

## 6. 统计与报告口径

`00_审计摘要.json` 必须包含：

```json
{
  "统计口径": "…人类可读的一句话…",
  "run_date": "YYYY-MM-DD",
  "window": {"since": "YYYY-MM-DD", "before": "YYYY-MM-DD"},
  "mail_scanned": 0, "mail_with_attachments": 0,
  "archive_invoice_count": 0,
  "included_invoice_count": 0, "excluded_invoice_count": 0,
  "included_total": 0.0, "excluded_total": 0.0,
  "category_totals": {}, "category_counts": {},
  "分类汇总PDF": [{"category": "", "invoice_count": 0, "amount": 0.0, "page_count": 0, "path": ""}],
  "wechat_source": {
    "inboundDir": "", "filesInWindow": 0, "invoiceFiles": 0, "ignoredByExtension": {}
  },
  "skipped": {
    "mails": [], "attachments": [], "duplicates": [], "orphan_itineraries": [],
    "wechat": [], "excludedByNumber": []
  }
}
```

- `skipped.excludedByNumber`：被排除清单剔除的票，每条含 `invoice_number` / `amount` / `reason` / `note` / `source`。

- `wechat_source`：微信来源的自检数字。`enabled=false` 时表示本次没收微信。
- `skipped.wechat`：**每个"像票据但没用上"的微信文件**都要有 `filename` + `reason`
  （md5 重复、图片不收、非 PDF、读取失败）。`.silk` 之类的非文档只体现在 `wechat_source.ignoredByExtension` 计数里，
  不逐条列出——否则一条语音消息就会往人工复核清单里塞一行噪音。

- `included_total` 必须等于所有 `计入总额=是` 记录的金额之和，且等于各分类金额之和，且等于合并 PDF 覆盖的金额。**三处对不上就是缺陷。**
- `skipped` **不得为空而不解释**：任何被跳过的邮件/附件都要留痕（硬约束 6）。

Excel `00_发票审计明细及汇总.xlsx` 两张表：

- **汇总**：标题 + 统计口径 + 左栏总体指标（归档张数 / 计入张数 / 待报销总金额 / 剔除张数 / 剔除金额）+ 右栏分类表（分类 / 计入张数 / 计入金额 / 合并PDF）+ 归档说明。
- **审计明细**：列序固定为
  `序号 | 抬头 | 用途 | 行程日期 | 地点或路线 | 票据类型 | 金额 | 发票号码 | 归档状态 | 金额口径 | 归档发票 | 计入总额 | 分类`
  发票号码按**文本**存储（20 位数字超出 Excel 精度）；冻结前 4 行与前 3 列。

## 7. 幂等与安全

1. 运行目录已存在且非空 → **拒绝覆盖**，退出码非零；`--force` 才允许清空重建。
2. 邮箱侧**只读**：绝不删信、绝不移动、绝不标已读（`markSeen=false`）。
3. 原始附件来源目录（`<参考案例根>\`）只读。
4. 授权码只从 DSH 配置库读取，日志中脱敏，绝不写入归档目录。
